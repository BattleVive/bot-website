## Project layout

- `app/main.py` - entry point.
- `app/battlevive_bot/battlevive/client.py` - high-level asynchronous Battlevive client and response parsing.
- `app/battlevive_bot/battlevive/supabase.py` - Supabase REST and authentication transport.
- `app/battlevive_bot/battlevive/tokens.py` - token validation and atomic persistent storage.
- `app/battlevive_bot/active_lobbies.py` - active-lobby polling, result evaluation, Discord reconciliation, and embed construction.
- `app/battlevive_bot/asset_manifest.py` - map asset manifest and lookup.
- `app/battlevive_bot/identity.py` - normalized member matching, active membership lookup, and safe recovery-link establishment.
- `app/battlevive_bot/refresh.py` - serialized upstream fetch and database snapshot coordination, including 30-second miss coalescing.
- `app/battlevive_bot/command_access.py` - opt-in public-command channel policy and in-memory cooldown enforcement.
- `app/battlevive_bot/` - Discord orchestration, database access, rendering, roles, models, logging, and settings.
- `app/init-db/` - PostgreSQL initialization schema.
- `app/assets/` - fonts, rank art, maps, champion emoji sources, and attribution.
- `app/data/` - local runtime state; production uses a dedicated bot data path.
- `infra/` - Terraform, SSM, monitoring, backup, recovery, and host automation.
- `utils/` - setup and environment-generation helpers.
- `tests/` - pytest suite.
- `app/requirements.txt` - direct runtime dependencies.
- `app/requirements.lock` - fully resolved hashed dependency lock.

## Validation

```bash
python -m compileall app utils
pytest
podman compose --env-file utils/.env \
  -f docker-compose.yml -f docker-compose.dev.yml up -d --build
```

`docker-compose.dev.yml` is an override: it builds the source once as
`battlevive-bot:local` and supplies local runtime settings, while the base file
defines PostgreSQL, persistent paths, networks, migrations, and health checks.
Never run the override by itself. The `--env-file` supplies Compose
interpolation values; set `BATTLEVIVE_ENV_FILE` only when the container
env-file lives elsewhere. The local override uses rootless Podman's `:U` mount
option so its fixed non-root bot user owns the persistent token directory.

Default pytest discovery must remain CI-safe. Browser login, real Discord calls, and real Battlevive calls belong behind an explicit manual integration gate.

## Refresh intervals

- tokens: every 30 minutes and after HTTP 401;
- users: hourly;
- lobbies, lobby slots, and season ratings: every 30 seconds;
- active-lobby details: every five seconds only while needed.

An unauthorized API request is retried once after token refresh.

## Data ownership

`user_discord_links` is canonical local recovery state, while `users.discord_id` is a dual-written active-user compatibility cache. Synchronization must preserve both and must not overwrite either from upstream payloads. Only a current `users` row grants membership.

Use `BattleviveClient` rather than adding Supabase transport directly to Discord command code. Keep endpoint transport in `supabase.py`, token persistence in `tokens.py`, and parsing behind client methods.

## Dependency changes

After editing `app/requirements.txt`, regenerate the lock:

```bash
uv pip compile app/requirements.txt \
  --output-file app/requirements.lock \
  --generate-hashes \
  --python-version 3.14 \
  --universal
```

Commit both files together and verify that the lock remains installable for Linux AMD64 and ARM64 Alpine builds.

## Continuous integration

The reusable quality workflow runs the hashed dependency set in this order: Python tests, Compose/migration checks, then AMD64 and QEMU ARM64 image smoke builds. Pull requests do not publish images.

Only a stable `vMAJOR.MINOR.PATCH` GitHub Release publishes Docker Hub tags. The workflow tests the exact tag commit, enforces main ancestry, calculates SemVer aliases with backport protection, builds the multi-platform image once, verifies its OCI revision and architectures, and emits SBOM and provenance. Production receives the immutable manifest digest through GitHub OIDC and the reusable deploy contract; ordinary `main` pushes never publish `latest`.

`infra/tools/validate.sh` defines the infrastructure static gate: Terraform formatting and validation, recursive TFLint, HIGH/CRITICAL Trivy configuration scanning, ShellCheck, JSON validation, and Bash parsing. Pull-request CI must assume the read-only plan role through `infrastructure-plan`, run that gate, and publish a sanitized `infra/tools/terraform-ci.sh plan` result. Protected main apply uses `infrastructure-apply` and the exact reviewed plan. Live AWS, Discord, browser, SSM, and restore probes remain behind documented manual gates and must not be discoverable by normal `pytest`.
