## Local and non-AWS deployment

Prepare local configuration, then build the source tree and start the complete
local Compose stack:

```bash
cd utils
cp .env.example .env
# Fill the required values in .env
./init.sh
cd ..
podman compose --env-file utils/.env \
  -f docker-compose.yml -f docker-compose.dev.yml up -d --build
```

`docker-compose.dev.yml` is an override, never a standalone file. It replaces
the published image with one local `battlevive-bot:local` build and supplies the
container env-file; `docker-compose.yml` supplies PostgreSQL, isolated
persistent paths, networks, migrations, and health checks. The rootless Podman
override assigns its persistent bot-data mount to the fixed non-root runtime
UID. The default token store is `app/data/bot/battlevive_tokens.json`. The base
Compose file uses bounded local container logs and does not require AWS.

## Production releases

Production is release-driven. Only stable GitHub Releases named `vMAJOR.MINOR.PATCH` publish images. A release such as `v1.5.1` produces `1.5.1`, `1.5`, `1`, `latest`, and `sha-<full-commit-sha>` tags when SemVer ordering permits those moving aliases. Backports update their minor alias but never downgrade `latest` or production.

The release workflow tests the exact tag commit, builds Linux AMD64 and ARM64 images with SBOM and provenance, and deploys the verified manifest as an immutable reference:

```text
voxix/battlevive-bot@sha256:<manifest-digest>
```

Ordinary pushes to `main` do not publish `latest`.

## AWS production layout and acceptance

The Terraform and host-automation contract targets one Systems Manager-managed EC2 instance in `eu-north-1`:

- its security group has no ingress rules and `sshd` is disabled only after a second SSM session succeeds;
- PostgreSQL is reachable by the bot only on the internal Compose backend network and is not published on the host;
- the bot and PostgreSQL use separate `/var/lib/battlevive/bot` and `/var/lib/battlevive/postgresql` paths;
- Parameter Store values are rendered under root:10001 mode-`0750` `/run/battlevive`, with root:10001 mode-`0640` files readable by the fixed runtime group;
- the release bundle is active at `/opt/battlevive/current`, and the only installed deploy executable is `/usr/local/libexec/battlevive/deploy`;
- application logs go to stdout and the AWS Compose override selects the provisioned `/battlevive/production/application` CloudWatch group;
- numbered migrations complete successfully before the bot starts;
- database and bot health must pass before a deployment is accepted.

Start an administrative session through the helper, which resolves the instance by project and environment tags:

```bash
infra/tools/ssm-session.sh
```

No inbound SSH rule or SSH key is required after the SSM transition is accepted. Before removing ingress or disabling `sshd`, prove a second new SSM session and CloudWatch session logging while the first session remains open.

## Deployment and rollback

The `battlevive-production-deploy` SSM document invokes the canonical installed executable. The command downloads a checksummed bundle from the operations bucket, holds the common operations lock, takes and verifies a pre-deploy database backup, pulls the exact image digest, runs migrations, and waits for database and bot health within a five-minute budget. It atomically records the version, digest, bundle key, and bundle checksum in `/battlevive/production/deployment/state` only after success.

If startup, health, or digest verification fails, the deployment script restores the previous bundle and digest. Database migrations must therefore remain compatible with at least the previous deployed image; automatic rollback does not downgrade the database.

## Backups and recovery

The configured weekly job creates a custom-format PostgreSQL archive, validates it with `pg_restore --list`, checksums it, and uploads a unique S3 key with a manifest. Weekly backups are retained for 84 days and pre-deploy backups for 30 days. The configured monthly job restores a backup under the common lock into an isolated temporary database and validates the expected schema and row-count manifest.

The recovery objective is a seven-day RPO and two-hour RTO. It is not accepted until a real S3 upload, checksum validation, isolated restore, alarm delivery, and timed recovery drill succeed. Verify the archive checksum and manifest, restore into an empty database, run pending migrations, start the exact known-good digest, and confirm health before resuming normal deployment.

## Instance sizing

Production stays on `t4g.micro` until 168 post-monitoring hours provide at least 98% of expected datapoints without a gap above two periods and satisfy every memory, swap, disk/inode, OOM, telemetry, bot-health, status-check, and CPU-credit gate. A resize to `t4g.nano` requires a fresh backup and snapshot plus 15 minutes of post-resize validation. Missing data or any failed gate keeps or restores `t4g.micro`.
