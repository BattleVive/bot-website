---
title: Troubleshooting
description: Diagnose startup, health, credentials, migrations, backups, and Discord behavior.
---

## Bot container does not start

Follow stdout logs with `podman compose logs -f bot`. Locally, run the base file and `docker-compose.dev.yml` override together, confirm `utils/.env`, the writable `app/data/bot` path, and a healthy database. If the error says a complete token pair is required, run `utils/init.sh`; it writes the bootstrap pair without printing it. On AWS, confirm root:10001 mode-`0640` files below mode-`0750` `/run/battlevive`, root-only non-secret `host.env`, the secret-rendering systemd unit, instance-role access to exact Parameter paths, and the `/battlevive/production/application` container log stream. Production does not use `.env` or write `app/logs` files.

## Credentials or token persistence fail

Local deployments default to the file token store and may regenerate credentials through `utils/init.sh`. AWS production uses the SSM token store and the EC2 role. Confirm the configured parameter and region without printing its SecureString. Three failed persistence attempts degrade the bot heartbeat; correct IAM or SSM availability and verify health recovers.

## Health is stale or unhealthy

The container health command accepts `/tmp/battlevive-health.json` only when its status is healthy and timestamp is no older than 90 seconds. Check Discord readiness, `SELECT 1`, each required background service, and token-persistence status. Docker does not restart a running container merely because it becomes unhealthy, so use the deployment/operations health gate to investigate or roll back.

## Migration fails

A migration checksum mismatch means an already-recorded SQL file changed. Restore the historical file exactly and create a new numbered migration; never rewrite production history. For SQL errors, inspect the migration service's stdout, correct the new migration, and rerun deployment. The advisory lock serializes concurrent runners.

## Database is unhealthy

Confirm `POSTGRES_PASSWORD_FILE`, the dedicated PostgreSQL host path, free disk/inodes, and the internal backend network. Bot traffic uses `db:5432`; PostgreSQL is not published on the production host. Do not delete or recursively change ownership of the production database directory.

## SSM access fails

Use `infra/tools/ssm-session.sh`, which resolves the tagged instance. Check instance status, SSM Agent, outbound connectivity, instance profile, and SSM association state. Do not reopen port 22 as a shortcut. During the initial transition, keep the first working session open until a second new SSM session succeeds.

## Backup or restore drill fails

Check the backup/restore systemd unit, operations bucket permissions, CloudWatch failure metric, available disk, archive checksum, `pg_restore --list`, and manifest. A deployment must abort when its pre-deploy backup fails; do not overwrite the live database to test an archive.

## Deployment rolled back

Inspect the custom SSM deployment command output plus dimensionless `Battlevive/Production` DeploymentFailure/DeploymentSuccess metrics for bundle checksum, image pull, migration, startup, digest, or health failure. Atomic `/battlevive/production/deployment/state` updates only after success and must be restored if rollback occurs. Keep the previous bundle and exact digest available, and do not move floating Docker tags manually to bypass the release workflow. A rollback is not accepted until its prior digest, database health, and bot health are reverified.

## Slash commands or roles fail

Container/CloudWatch logs usually identify missing Discord permissions, unavailable upstream credentials, or database failures. For command policies, cooldowns, ambiguous identity, active-lobby roles, and recovery links, inspect `/config show` and the relevant feature page. Leave `DISCORD_COMMAND_GUILD_ID` blank in production; global command updates can take time.
